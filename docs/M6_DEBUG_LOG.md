# Milestone M6 物理烧录与实机验证调试记录 (M6 Physical Flashing & Device Verification Debug Log)

**日期**：2026-07-20  
**阶段**：M6 受控硬件验证  
**固件基线**：`x12-1024.img` (官方原件)  
**测试对象**：`x12-purified.img` (二次重打包固件)  

---

## 1. 调试事件与现象记录

### 事件一：PhoenixCard 格式化报错 242
*   **现象**：在 Windows 端使用 PhoenixCard (量产 Product 模式) 尝试写入 TF 卡时，弹出“正在格式化卡... 格式化卡 E 失败 242”错误。
*   **归因**：TF 卡底层引导扇区或异常分区表被系统进程锁定，或存在 Allwinner 历史写保护残留分区，导致工具无法获取磁盘排他性控制权并执行底层擦除。
*   **解决路径**：使用 Windows `diskpart` 命令行工具，通过 `clean` 指令强行清空磁盘物理签名，重建主分区并快速格式化为 FAT32。处理后 PhoenixCard 成功识别并完成烧录。

### 事件二：刷机进度死锁与 LED 高频报警
*   **现象**：将烧录了 `x12-purified.img` 的 TF 卡插入 UBOX10 实机通电后，屏幕/工具进度条停滞在 5%-10% 处超过 3 分钟。同时，前置面板 LED 指示灯呈现**高频交替闪烁（蓝绿）**。
*   **逻辑判定**：
    *   0-5% 为 BootROM 加载 U-Boot 阶段。
    *   5-10% 为 U-Boot 初始化 eMMC 并准备擦除/写入分区表及主数据块（如 `super.fex`）阶段。
    *   LED 高频闪烁系全志刷机引擎 (`sprite`) 遭遇 Fatal Error 触发系统挂起 (panic) 的硬件级报警。

### 事件三：对照组实验（官方固件验证）
*   **方法**：为排除物理介质（TF卡、读卡器）与烧录流程的干扰，使用完全相同的硬件条件与 PhoenixCard 参数，将未修改的官方原厂包 `x12-1024.img` 写入 TF 卡并上电实测。
*   **现象**：刷机进度顺利跨越 10% 瓶颈并最终闭环。前置面板 LED 指示灯呈现**低频交替闪烁（约 1s 周期）**。
*   **实验结论**：物理硬件链路与 TF 卡引导机制 100% 正常。刷机死锁问题确定由二次打包的定制固件 `x12-purified.img` 内部结构缺陷导致。

---

## 2. 根本原因推演

对照组实验确证了 `sprite` 引擎的低频闪烁代表正常 I/O 写入，高频闪烁代表 I/O 或内存错误阻断。结合卡在数据写入前夕的进度节点，错误原因高度指向以下两点：

1.  **动态分区 (`super`) 物理边界越界**：在前期离线重建测试中，曾将 `product` 逻辑分区伸缩至 320MB 并重新构建了 `super` 逻辑卷。如果 `lpmake` 重排后生成的 `super.img` 总字节数超过了全志底层物理分区表 (`sys_partition.fex`) 分配给 `super` 块的绝对磁道容量，U-Boot 在执行校验或写入时会立即触发边界溢出 (Out of space/Boundary error) 并 Halt。
2.  **文件对齐与稀疏格式异常**：`super.img` 未能被正确转化为全志兼容的 Sparse Image 格式，或文件在重组打包时的 1024 字节对齐机制存在偏差，导致 U-Boot 解析元数据失败。

## 3. 后续行动计划 (Next Steps)

当前盲测已达极限，需引入精确测量和底层日志机制进行阻碍破除：

*   **行动 1：静态体积测量与约束**  
    对比提取的原厂 `super.fex` 与我们通过 `lpmake` 生成的 `super.img` 的精确字节数。若体积超标，需通过脚本重新限定 `super` 卷的最大上限，利用前期精简释放的 ~300MB 空间，确保修改后的分区体积 $\le$ 原厂物理边界。
*   **行动 2：建立 UART 硬件级诊断**  
    在 PCB 上焊接 J21 串口排针，使用 USB 转 TTL 模块（波特率 115200）直连电脑。在刷写 `x12-purified.img` 触发死锁时，通过串口终端直接抓取 U-Boot 输出的底层异常栈 (Exception Stack)，以此作为调整打包脚本或分区块参数的唯一判定事实。

### 4. 二次实机刷写测试 (引入 img2simg 稀疏化)

*   **方法**：为验证是否为 Sparse 格式兼容性问题导致的解析错误，在 M4 重打包流程中引入 AOSP `img2simg` 工具，将 Raw ext4 转换为标准 Sparse 镜像后，再次重组 `x12-purified.img` 并进行量产卡刷写[cite: 15]。
*   **现象**：与首次测试现象完全一致。进度停滞在 5%-10%，前置面板 LED 再次呈现**高频交替闪烁（蓝绿）**[cite: 11, 15]。
*   **实验结论**：这证明单纯的 AOSP Sparse 格式不兼容并非导致全志 `sprite` 引擎挂起的核心原因。故障域被进一步收窄：极大概率是 `super` 分区的绝对物理体积溢出（打破了 `sys_partition.fex` 的底层边界），或者是 `pack_image.py` 封装时 1024 字节文件头偏移量存在扇区对齐错位[cite: 14]。盲目打包尝试已无意义。
